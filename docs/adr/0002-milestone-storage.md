# 2. אבני דרך נשמרות כשדות, ורשימה אחת מתארת אותן

תאריך: 2026-09-08

## סטטוס

מקובל

## הקשר

ההנהלה ביקשה ארבע אבני דרך חדשות לקמפיינים — בקרה, הקפאה, הודעה לחברה, סיום
קמפיין — בנוסף לתאריך התחלת עבודה שנוסף בהחלטה [0001](0001-work-start-date.md).
יחד עם תאריך ההתנעה הקיים, אלה שישה מועדים אופציונליים ברזולוציית יום על אותה
ישות.

הדרישה הייתה כפולה וסותרת לכאורה: "מודל שאפשר להרחיב בעתיד" מצד אחד, "אל תבנה
מערכת מורכבת של ניהול אבני דרך" מצד שני.

נשקלו שתי אפשרויות:

1. עמודה לכל מועד בטבלת האירועים.
2. טבלת `event_milestones` נפרדת עם עמודת `kind`.

## החלטה

נבחרה אפשרות 1 — **עמודה לכל מועד**, ובנוסף **רשימת מטא-דאטה אחת בקוד** שמתארת
כל מועד: מפתח, השם שהעובד רואה, הסבר, צבע, אייקון, סדר על ציר הזמן, ולאילו
קטגוריות אירוע הוא רלוונטי.

הטופס, לוח השנה, ציר הזמן, פרטי האירוע, המקרא והייצוא **קוראים כולם מהרשימה
הזאת** ואינם מחזיקים רשימת מועדים משלהם.

## נימוק

ההנחה שטבלה נפרדת = "יותר גמיש" לא החזיקה בבדיקה. הוספת מועד שביעי:

| | עמודות | טבלה נפרדת |
|---|---|---|
| מיגרציה | עמודה חדשה | ערך חדש ב-enum |
| רשימת מטא-דאטה | שורה אחת | שורה אחת |
| עדכון מסכים | אפס — נגזר מהרשימה | אפס — נגזר מהרשימה |

הגמישות האמיתית יושבת ברשימה, לא בצורת האחסון. מה שהטבלה **כן** מוסיפה הוא
עלות קבועה: join בכל קריאה, כתיבה נפרדת, פיבוט בייצוא, וזכירה להעתיק שורות
בשכפול לוח — נקודת כשל שקל לשכוח ושקטה כשהיא נשברת. עמודות מועתקות בשכפול לוח
מעצמן.

הטבלה תשתלם רק אם מועדים יהפכו למוגדרים-על-ידי-משתמש לכל לוח. זו יכולת שלא
התבקשה ושהוגדרה במפורש כמחוץ לגבולות.

## תוצאות

**חיובי**
- שכפול לוח, ייצוא ל-CSV, חיפוש ו-API ממשיכים לעבוד בלי שינוי מבני.
- כל מועד מאומת בסכמה כמו כל שדה אחר, ולא בקוד ידני לכל `kind`.
- מסך חדש שמציג אבני דרך מקבל את כולן אוטומטית מהרשימה.

**שלילי**
- טבלת האירועים מתרחבת בשש עמודות תאריך. קריאה ישירה של הטבלה נעשית רחבה יותר.
- אם יידרשו מועדים לכל לוח, תידרש הגירה לטבלה נפרדת. ההחלטה הזאת מקבלת את
  הסיכון במודע: ההגירה אפשרית, והמחיר של לבנות אותה מראש גבוה יותר מהסיכוי
  שתידרש.
